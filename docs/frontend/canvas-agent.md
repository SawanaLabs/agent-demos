# Canvas Agent

- Route: `/demos/canvas-agent`; feature boundary: `apps/web/features/canvas-agent`.
- Reuse generic AI Elements Canvas/Node primitives. Keep workflow semantics feature-local; the older Image Workflow Agent retains its single-generator contract.
- `model/graph.ts` owns schema validation, acyclic dependency ordering, atomic definition changes, and descendant output invalidation. Position and label changes preserve generated results.
- Canvas Agent and text generation share the global `openai/gpt-5.6-luna` default and explicitly send `providerOptions.openai.reasoningEffort: "medium"`. `AI_GATEWAY_CHAT_MODEL` can override the model. Image generation keeps its separate defaults.
- Canvas image generation defaults to `openai/gpt-image-2` with `providerOptions.openai.quality: "low"` via `generateImage`. `AI_GATEWAY_IMAGE_MODEL` can override the model. Reference inputs use `prompt.images`. Output sizes are 1024×1024, 1536×864, and 864×1536 for the three canvas ratios.
- Agent tools and manual edits share this graph model. Agent requests carry the latest graph; image payloads are omitted from the agent's system context. Generation nodes receive connected text and images as multimodal inputs.
- The Agent defaults to execute mode but runs only on explicit generation requests. New canvas clears the graph and conversation. `readWorkflow`, `addNode`, `removeNodes`, `updateNode`, `connectNodes`, `disconnectNodes`, `runWorkflow`, and `arrangeCanvas` cover inspection, graph edits, execution, and browser-measured layout. `addNode` adds one node with explicit upstream `sourceIds`, preserving the rest of the workflow. `removeNodes` removes only the specified nodes and incident edges without rewriting retained definitions. Follow-up generation creates a connected node and runs that target, retaining earlier outputs. Layout requests apply after streaming finishes.
- Agent edits use SDK `tool` schemas for one node or edge. `model/commands.ts` applies patches through the shared graph validator/invalidation rules. Whole-graph replacement is not an Agent tool: unchanged nodes never need to be regenerated by the model. Edit tools report which outputs became invalid. See [AI SDK tools](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling).
- Plan mode does not expose an execution tool. Execute mode permits sequential execution tool calls within AI SDK’s `stopWhen: stepCountIs(12)` loop, only on a generation request. There is no extra once-per-turn execution guard. Tool operations are serialized. Graphs have at most 20 nodes and 60 edges.
- Agent execution defaults to `mode: resume`: whole-graph and targeted runs reuse successful outputs and execute missing/failed nodes. Explicit `regenerate` replaces the target (or every node for a whole-graph run); manual run buttons retain this regeneration behavior. Replacement happens only after success, then dependent outputs are invalidated. A failed replacement preserves the previous successful output and marks the node failed; resume retries it even when an old output exists. Unrelated branches stay intact. Tool results report mode, attempted/completed/reused nodes and invalidated descendants on both success and failure.
- Manual execution streams NDJSON snapshots; agent execution streams transient `data-canvas` events through AI SDK. Closing the conversation view never unmounts its controller.
- Tool calls stay in AI SDK message-part order, interleaved with text and reasoning. The feature-local CanvasTool composes AI Elements Tool/ToolContent with a compact collapsible trigger; successful details are opt-in, errors and interrupted operations remain visible without expanding. Do not regroup tools above assistant text or reorder streamed parts. The agent briefly introduces the first action and workflow execution, then reports the actual result.
- Conversation uses AI Elements PromptInput, Message, Reasoning and Tool with AI SDK `useChat` statuses, `stop`, and `regenerate`. Submitted/streaming requests remain visibly active, including before the first text token. Empty reasoning parts are hidden. Transport failures always render a conversation error bubble, even when a failed HTTP response or SDK error has no message; collapsed chat retains an error indicator. HTTP errors are normalized without displaying server response bodies. There is no automatic generation retry.
- Retry before any tool work uses SDK `regenerate`. After tool work or an interrupted tool request, continuation preserves tool history and sends the current graph with instructions to reuse completed results and unfinished nodes. Stopping cancels the request and retains snapshots already received; it does not guarantee a provider has stopped processing or reverse external side effects. A new multi-deliverable request builds all branches before its single execution; follow-ups target only new work. See [AI SDK chat](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot) and [AI Elements PromptInput](https://elements.ai-sdk.dev/components/prompt-input).
- All model-backed routes use host metering. Node failures preserve diagnostic messages and expose error name, code, SDK HTTP status/retryability and bounded cause chains to the Agent. Credentials are redacted; request headers/bodies and stacks are not serialized. Graph definitions and conversation live in browser state; manual JSON export/import persists a workflow. Images are stored in the existing public Vercel Blob store; graph fields hold URLs. No automatic graph reload recovery is claimed.
- Hide the host companion on this full-screen route to avoid overlapping the workflow composer. Keep the host theme toggle accessible beside the header.
- The catalog lists this Agent Demo as ready and explicitly omits registry export until its portable export is prepared.
- Video generation and depth extraction are not supported graph operations. `/tools/depth-video` is a separate browser tool.

- Node execution and input failures are stored by node ID in `graph.errors` and streamed with graph snapshots. Render them inside the feature node using the shared shadcn Alert; graph-level or transport failures remain in the conversation. Retrying clears an individual error when its node is attempted; editing inputs clears affected node and descendant errors. Older exports default to an empty error map.

- Toolbar exposes image/text generators, image/text materials, and a terminal output display. `prompt` materials pass literal text unchanged; `reference` materials pass uploaded images. Neither calls a model. Generators may receive their prompt entirely from upstream text. `output` accepts multiple inputs and displays materials immediately and generated outputs as available; it has no outgoing edges and makes no model calls.
- Image and generated text outputs appear as separate draggable result cards via `model/presentation.ts`. Both result cards and terminal preview nodes display text/images and provide image downloads and UTF-8 TXT downloads. The toolbar calls the terminal display `预览输出`; its persisted kind remains `output`. These cards project the generator output, retaining the generator ID as the executable dependency; they do not duplicate assets or add executable nodes. View IDs are namespaced. Optional `node.resultPosition` persists result placement. Rerunning updates the same card; input edits invalidate stale results. Cards can connect to downstream generators or displays.
- Automatic result cards and manually added previews both render `CanvasOutputView` using the same `display` view type, width, header, content list, and downloads. Automatic results supply one item and a continuation action/source handle; manual previews collect connected inputs and expose deletion. Automatic results retain `result:` IDs and generator-owned data/position, so they do not add graph nodes or change execution dependencies.
- Feature-local node styles override Card overflow and enlarge XYFlow handles so manual connections remain accessible.
- Controlled React Flow nodes retain `measured`, selection, and drag state in the UI layer through `applyNodeChanges`, including dimension events during execution. Workflow projections own content and persisted positions. Dropping `measured` when rebuilding node objects makes React Flow hide all affected nodes until remeasurement, causing drag flicker. See [official node changes](https://reactflow.dev/api-reference/utils/apply-node-changes) and [v12 measured dimensions](https://github.com/xyflow/xyflow/discussions/3764).

- `整理画布` sits with zoom and fit-view controls at the top left. Dagre lays out the visible graph left-to-right using measured node sizes, including generated result cards and disconnected nodes. It changes only node/result positions, preserves content and connections, and fits the viewport after arranging. It is disabled during generation.

- `gif` is a **content processing** node: exactly one upstream grid image, configurable rows/columns (1–4 each) and fps (1–24). Sharp slices equal cells left-to-right, top-to-bottom, caps each frame at 512 pixels per side, then encodes a looping GIF with per-frame delays. It uses no generation model; model calls are only needed if an upstream image must be generated. Changing GIF settings invalidates its result and descendants, preserving the source grid. It does not interpolate frames or correct inconsistent AI poses/gutters.
- GIF results use `output.image` with `image/gif`, appear as separate result cards, animate in previews, and download with `.gif`. Workflow JSON round-trips GIFs. If passed into an AI generator, a GIF supplies its first frame as PNG; use the original grid for character consistency across follow-up generation.
- Successful Agent runs request measured canvas layout automatically. The reference conversation is: empty canvas → describe a 2×2 character grid → “做成 GIF” → request a consistent 4×4 turntable and GIF. Users can complete this through conversation alone; manual node operations remain optional.

- Canvas images reuse `BLOB_READ_WRITE_TOKEN` and the public Blob store. Browser uploads use the official `@vercel/blob/client` direct-upload flow with a short-lived server token; binary files bypass the application request body. Token issuance checks same-origin, visitor-scoped paths, image MIME types, and an 8 MiB per-file limit. A best-effort visitor/day listing caps uploads at 20 files or 64 MiB (concurrent token requests are not an atomic quota). See [Vercel client uploads](https://vercel.com/docs/vercel-blob/client-upload).
- Uploaded files use `canvas-agent/uploads/`; generated images and GIFs use `canvas-agent/results/`. Execution stores results before publishing graph snapshots. Only execution resolves image URLs into bytes, with bounded reads and an allowlist of public Blob image paths. Images remain public to anyone with their URL, matching the existing store access mode.
- Legacy Base64 JSON imports remain readable. Before chat or execution, the browser uploads embedded images once per distinct value and replaces references with URLs. New workflow exports reference Blob URLs, so they depend on those objects remaining available. Removing a node does not delete its Blob; automatic asset retention/cleanup is not implemented. Image download links use Blob's `download=1` response behavior.

- Published-site usage reserves one request credit, then resource credits before each executed text/image generator. Cached results and GIF processing do not add generation credits. Insufficient credits appear as node errors while completed upstream outputs remain reusable; host prices live outside this demo.

- Text and image generators accept `resultCount` (1–4, default 1), editable through a shadcn Select or Agent node tools. Single-result nodes retain their existing `{text}` / `{image}` output contract. Multiple results use `output.results`, an ordered list of labeled text/image items; old workflow files remain readable.
- Multi-text generation uses AI SDK `generateText` with `Output.object` and a schema requiring exactly the requested number of `{label, text}` results. The prompt defines the deliverables and their order. No Markdown/title parsing is used. Multi-image generation uses native `generateImage({n})` and `result.images`, keeping GPT Image 2 low. See [structured output](https://ai-sdk.dev/docs/reference/ai-sdk-core/output) and [multiple image generation](https://ai-sdk.dev/docs/ai-sdk-core/image-generation).
- Each result has its own preview card and downstream connection. Optional zero-based `edge.resultIndex` selects one result; omission carries every result and always draws the connection from the generator, regardless of execution state. Connecting a result card or clicking its continuation button selects that result. Agent `connectNodes`/`disconnectNodes` use the same selector. Reducing count below an existing selected result requires disconnecting that edge first; connections are never silently reassigned.
- Result cards retain stable IDs by generator and index. The first card keeps the legacy ID/`resultPosition`; additional positions persist in `resultPositions`. Layout, dragging, imports, downloads, and manual terminal previews support each item. Any result-count change invalidates that generator and descendants.
- One multi-text request consumes one text-generation operation. An image batch reserves `count` image operations atomically before calling the provider, using the host's existing credit transaction. A denied batch cannot leave partial batch charges.
- Opt-in provider verification: `CANVAS_GENERATION_INTEGRATION=1 pnpm --dir apps/web test:integration features/canvas-agent/server/multi-results.integration.test.ts`. This calls the real Agent, generates two text results with separate preview connections, and generates/stores three images. It incurs provider usage and verifies the feature service independently of the HTTP/database usage gate.

- Canvas Agent conversations are free, including at zero credits. The host route skips only its base message charge; generation nodes still use the same request-scoped resource meter. Manual workflow requests retain their base charge.
- Workflow node failures return tool outcomes with a failed node, diagnostic error, failure code, execution report, and retained completed node labels. Credit denials also carry required/remaining credits and reset time through the portable resource hook. The Agent continues its conversation from these facts; it must not automatically retry quota denials, invent refund/reset facts, or suggest model configuration changes for insufficient credits. Completed outputs remain reusable. Only genuine conversation/transport failures use the chat retry bubble. If a failed tool result already exists, continuing an interrupted conversation asks for an explanation only and does not request another generation attempt. Expected quota denials are excluded from provider-failure telemetry.
- `pnpm --dir apps/web test:integration features/canvas-agent/server/workflow-failure.integration.test.ts` verifies a real Agent explains a denied node after the tool result, without a stream error. Its resource observer rejects generation before any image provider call; the Agent request itself uses the real text provider.

- With local Next.js running, `SITE_USAGE_DATABASE_INTEGRATION=1 pnpm --dir apps/web test:integration features/canvas-agent/server/credit-workflow.integration.test.ts` gives a unique test visitor three remaining credits and calls the real HTTP route. It verifies text generation spends one credit, the image node is denied at two remaining credits, the Agent explains the partial result, and a subsequent node edit is free. It then restores the synthetic visitor’s allowance outside the chat request and verifies a resumed real image generation preserves the earlier text and charges only the image operation. The test removes only its own visitor and cascading usage rows.

- Generator result slots are visible from planning time, one per configured result, and survive output invalidation with an empty waiting state. Selected-result edges always originate from that slot; all-results edges always originate from the generator. Execution never relocates a connection or a result slot. Count changes update slots, never infer counts or generation costs from downstream fan-out. Automatic result target handles are reserved for the generator-owned edge and reject user connections; manual terminal previews accept connections and collect content without affecting generation counts.
- Canvas Agent system instructions hold interaction, preservation, execution-consent and failure principles. Node schemas and tool descriptions own node kinds, result-count semantics, selected-result wiring, GIF recipes and execution targeting. Tool descriptions are visible to the model before tool selection, not lazily loaded at invocation; this separation improves contract ownership, not automatic context savings. See [AI SDK tools](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling).
- `pnpm --dir apps/web test:integration features/canvas-agent/server/planning.integration.test.ts` checks real Agent planning for separate prompts versus a shared brief. It calls the text provider but performs no node generation.

- Node headers include type icons. Connected-input badges above generator instructions identify the source node, selected result and text/image type; missing content is marked waiting rather than presented as ready. Badges follow graph edges and disappear when disconnected. Result and terminal-preview headers show text/image badges, including both types for mixed previews; empty result slots use their planned type. These are display projections only and never modify prompts, connections, execution or billing.

- `pnpm --dir apps/web test:integration features/canvas-agent/server/recovery.integration.test.ts` uses the real Agent model and AI SDK loop with an injected node-provider timeout. It verifies the Agent receives the diagnostic error, retries that node, then executes a different node within the same turn. A second case changes the injected resource allowance between chat requests, retaining the same graph and tool history, and verifies only unfinished work executes after a top-up. These controlled tests do not validate the database or image provider. They exercise [AI SDK loop control](https://ai-sdk.dev/docs/agents/loop-control) without a custom agent loop.

- Generator creation uses one shared command for UI and Agent: independent text/image generation creates a prompt material plus generator and automatic result previews. Instructions supplied to `addNode` become a connected prompt material; the generator itself has no editable prompt field. Continuing from an existing result with no new instructions adds only the generator and its result previews. Text inputs are concatenated in connection order, in full; images are passed as model image inputs.
- Agent creation outcomes return the prompt material ID, actual input connections, result references and the input contract. Attempts to edit inline generator prompts or connect a generator without a result index receive actionable tool errors. Running a material as a target returns a non-generation result with connected execution targets, preventing a no-op from being reported as generated content. System instructions remain unchanged for this experiment. Legacy `sourceIds` connections expand to explicit result references, preserving their all-results meaning.
- Generator source handles are reserved for automatic result-preview edges; users connect downstream from the result previews. Manual terminal outputs keep their collection-only role. Opening an older workflow moves inline instructions into prompt materials, expands all-result edges, and retains completed outputs, errors and result positions. Prompt material outputs are seeded during migration so resuming does not invalidate retained work. Graph capacity allows 40 nodes / 260 edges to accommodate the prior 20-node / 60-edge format after expansion.
